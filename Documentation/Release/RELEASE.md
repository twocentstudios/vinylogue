# Vinylogue Release Manual

This checklist is for semi-automated releases performed by an agent. The human creates the new app version in App Store Connect, handles review/release decisions, and resolves Apple account authentication when required. The agent normally handles the repository changes, verification, signed archive, CLI upload, GitHub bookkeeping, tag, and GitHub Release.

Repository constants:

```sh
REPOSITORY="twocentstudios/vinylogue"
PROJECT="Vinylogue.xcodeproj"
SCHEME="Vinylogue"
TEAM_ID="YK25EF78NT"
BUNDLE_ID="com.twocentstudios.vinylogue"
```

The release spans multiple shells and may span several days. Treat the variables in this manual as examples: record the exact version, build number, archive-producing commit, PR number, and milestone number in the agent's durable work log, then restore or substitute them before each later step.

## 1. Establish the release scope

- [ ] Read the repository instructions, especially `CLAUDE.md`.
- [ ] Confirm the release version with the human. Use SemVer, for example `2.0.2`.
- [ ] Identify every merged PR shipped since the previous tag.
- [ ] Draft user-facing release notes from those PRs.
- [ ] Put significant non-user-facing work in a separate `Engineering Notes` section. Do not mix implementation details into `What's New` unless they matter to users.

### GitHub Release screenshots

- [ ] Decide whether GitHub Release screenshots are warranted. Include them only for visible new features.
- [ ] Select them from the descriptions or comments of the PRs included in the release.
- [ ] Prefer a small set that directly illustrates the user-facing changes.
- [ ] If the selection is ambiguous, ask the human which PR screenshots to include. Do not invent a selection.
- [ ] Record the selected images, filenames, descriptions, and source PRs for the GitHub Release step.

GitHub Release screenshots are optional release-note illustrations. They are separate from the screenshots uploaded to App Store Connect.

### App Store Connect screenshots

- [ ] Ask the human whether the existing App Store screenshots should be retained or replaced for this release.
- [ ] If replacements are needed, plan the screen sequence, feature coverage, pixelation choice, device sizes, and any copy or test-data changes with the human before running tests.
- [ ] Inspect `VinylogueAppStoreScreenshotUITests/AppStoreScreenshotTests.swift`. The current suite captures Users, Weekly Albums, and Album Detail using mock data, with both unpixelated and pixelated variants.
- [ ] Inspect `generate-app-store-screenshots.zsh` and update its hardcoded simulator models and `DEVICE_OS` when they do not match installed runtimes or current App Store requirements.
- [ ] Get explicit human approval before running the screenshot UI tests, as required by `CLAUDE.md`.
- [ ] Run the generator only after the content and configuration are approved.
- [ ] Visually review every generated image in `DerivedData/UITestingScreenshots`. Do not upload the test output blindly.
- [ ] Ask the human to approve the final App Store screenshot set and upload it in App Store Connect.

App Store Connect screenshots are a planned store-listing deliverable generated by the UI-test workflow. Do not substitute screenshots pulled from PRs unless the human explicitly chooses to do so.

Create or reuse the milestone for this release, then assign every shipped PR to it:

```sh
RELEASE_VERSION="2.0.2"

gh api "repos/$REPOSITORY/milestones?state=all&per_page=100" \
  --paginate \
  --jq ".[] | select(.title == \"$RELEASE_VERSION\") | [.number, .state, .html_url] | @tsv"

gh api --method POST "repos/$REPOSITORY/milestones" \
  --field title="$RELEASE_VERSION" \
  --field description="Vinylogue $RELEASE_VERSION"
```

Create the milestone only if the lookup returned nothing. Record its numeric `number`, not the release version string, for API updates:

```sh
MILESTONE_NUMBER="<number>"
PR_NUMBER="<shipped-pr-number>"

gh api --method PATCH "repos/$REPOSITORY/issues/$PR_NUMBER" \
  -F milestone="$MILESTONE_NUMBER"
```

## 2. Prepare the version-bump PR

- [ ] Start from a clean, current `master`.
- [ ] Generate a unique timestamp build number in the project timezone.
- [ ] Create a release branch matching repository precedent.

```sh
git switch master
git pull --ff-only origin master
git status --short

RELEASE_VERSION="2.0.2"
BUILD_NUMBER="$(TZ=Asia/Tokyo date +%Y%m%d%H%M%S)"
RELEASE_BRANCH="version-bump-v$RELEASE_VERSION"

git switch -c "$RELEASE_BRANCH"
```

- [ ] Set `MARKETING_VERSION` to the release version in `project.yml`.
- [ ] Set `CURRENT_PROJECT_VERSION` to the timestamp build number in `project.yml`.
- [ ] Run XcodeGen from the repository root to regenerate `Vinylogue.xcodeproj`.
- [ ] Do not edit `project.pbxproj` manually.

```sh
xcodegen
```

> Footgun: the `2.0.1` release edited the generated Xcode project without updating `project.yml`. A later XcodeGen run could therefore restore the old version. Treat `project.yml` as the source of truth and the Xcode project as generated output.

Verify the values and diff:

```sh
rg -n "MARKETING_VERSION|CURRENT_PROJECT_VERSION" \
  project.yml Vinylogue.xcodeproj/project.pbxproj
git diff --check
git diff -- project.yml Vinylogue.xcodeproj/project.pbxproj
```

- [ ] Confirm XcodeGen propagated the requested version and build number into the generated project.
- [ ] If XcodeGen changed anything unrelated to the intended project configuration, stop and investigate the generator or spec version before committing.

- [ ] Commit using the existing format.
- [ ] Push the branch.
- [ ] Open a normal, non-draft PR against `master`.
- [ ] Assign the release PR to the release milestone.
- [ ] Do not merge the release PR yet. The current convention is to merge after the App Store version is approved and released.

```sh
git add -- project.yml Vinylogue.xcodeproj/project.pbxproj
git commit -m "Version Bump $RELEASE_VERSION $BUILD_NUMBER"
git push -u origin "$RELEASE_BRANCH"

gh pr create \
  --repo "$REPOSITORY" \
  --base master \
  --head "$RELEASE_BRANCH" \
  --title "Version Bump $RELEASE_VERSION" \
  --body "Version bump to $RELEASE_VERSION ($BUILD_NUMBER)"
```

Record the exact commit that will produce the archive:

```sh
ARCHIVED_COMMIT="$(git rev-parse HEAD)"
```

Persist this SHA; do not rely on the shell variable surviving App Store review.

## 3. Verify the release candidate

- [ ] Confirm the branch is clean and synchronized with its remote.
- [ ] Run the full unit suite on the configured simulator.
- [ ] Build the Release configuration.
- [ ] Do not run UI tests unless the human explicitly requests them, per `CLAUDE.md`.

Use the simulator destination documented in `CLAUDE.md`:

```sh
SIMULATOR_UDID="<UDID-from-CLAUDE.md>"

set -o pipefail
xcodebuild \
  -project "$PROJECT" \
  -scheme "$SCHEME" \
  -destination "platform=iOS Simulator,id=$SIMULATOR_UDID" \
  -derivedDataPath DerivedData \
  -configuration Debug \
  test 2>&1 | xcsift -w

set -o pipefail
xcodebuild \
  -project "$PROJECT" \
  -scheme "$SCHEME" \
  -destination "platform=iOS Simulator,id=$SIMULATOR_UDID" \
  -derivedDataPath DerivedData \
  -configuration Release \
  build 2>&1 | xcsift -w
```

- [ ] Require zero test failures and zero build errors.
- [ ] Investigate new warnings before continuing.

## 4. Human App Store Connect setup

Before upload, ask the human to:

- [ ] Create version `$RELEASE_VERSION` for Vinylogue in the App Store Connect web UI.
- [ ] Confirm the version is ready to receive the build.
- [ ] Confirm the user-facing `What's New` text and release behavior.

The agent does not create the App Store Connect version or make the final review/release decision.

## 5. Create the signed archive

- [ ] Confirm Xcode is signed into the correct Apple account.
- [ ] Confirm the project uses team `YK25EF78NT` and automatic signing.
- [ ] Archive the same clean commit recorded as `ARCHIVED_COMMIT`.

```sh
ARCHIVED_COMMIT="<persisted-archive-producing-commit>"

test "$(git rev-parse HEAD)" = "$ARCHIVED_COMMIT"
test -z "$(git status --porcelain)"

ARCHIVE_PATH="$PWD/DerivedData/Archives/Vinylogue-$RELEASE_VERSION-$BUILD_NUMBER.xcarchive"

set -o pipefail
xcodebuild \
  -project "$PROJECT" \
  -scheme "$SCHEME" \
  -configuration Release \
  -destination "generic/platform=iOS" \
  -derivedDataPath DerivedData \
  -archivePath "$ARCHIVE_PATH" \
  -allowProvisioningUpdates \
  archive 2>&1 | xcsift -w
```

If Xcode reports that the Apple account login was rejected or that no iOS signing identity with a private key exists, stop. Ask the human to sign into Xcode and let Xcode create or download the current certificate. Do not work around account or certificate failures.

Verify the archive metadata:

```sh
/usr/libexec/PlistBuddy \
  -c 'Print :ApplicationProperties:CFBundleIdentifier' \
  "$ARCHIVE_PATH/Info.plist"
/usr/libexec/PlistBuddy \
  -c 'Print :ApplicationProperties:CFBundleShortVersionString' \
  "$ARCHIVE_PATH/Info.plist"
/usr/libexec/PlistBuddy \
  -c 'Print :ApplicationProperties:CFBundleVersion' \
  "$ARCHIVE_PATH/Info.plist"
```

- [ ] Bundle identifier is `com.twocentstudios.vinylogue`.
- [ ] Short version equals `$RELEASE_VERSION`.
- [ ] Build version equals `$BUILD_NUMBER`.

## 6. Upload from the CLI

Use the checked-in `ExportOptions.plist` stored beside this manual. It contains no credentials and should not need per-release edits.

```sh
EXPORT_OPTIONS="$PWD/Documentation/Release/ExportOptions.plist"

plutil -lint "$EXPORT_OPTIONS"
/usr/libexec/PlistBuddy -c 'Print :destination' "$EXPORT_OPTIONS"
/usr/libexec/PlistBuddy -c 'Print :method' "$EXPORT_OPTIONS"
/usr/libexec/PlistBuddy -c 'Print :manageAppVersionAndBuildNumber' "$EXPORT_OPTIONS"
/usr/libexec/PlistBuddy -c 'Print :teamID' "$EXPORT_OPTIONS"
```

- [ ] `destination` is `upload`.
- [ ] `method` is `app-store-connect`.
- [ ] `manageAppVersionAndBuildNumber` is `false`.
- [ ] `teamID` is `YK25EF78NT`.

> Footgun: keep `manageAppVersionAndBuildNumber` set to `false`. Otherwise Xcode may replace the timestamp build number during upload, breaking the link between Git, the archive, and App Store Connect. If a future Xcode release deprecates an export key, update the checked-in plist deliberately and review that change like release tooling.

Upload the archive:

```sh
EXPORT_PATH="<absolute-temporary-export-directory>"

xcodebuild \
  -exportArchive \
  -archivePath "$ARCHIVE_PATH" \
  -exportPath "$EXPORT_PATH" \
  -exportOptionsPlist "$EXPORT_OPTIONS" \
  -allowProvisioningUpdates
```

- [ ] Keep the raw export output and require an explicit successful upload result.
- [ ] Report the uploaded version and build number to the human.
- [ ] Wait for App Store Connect processing.
- [ ] Ask the human to select the processed build, finish metadata/compliance, and submit it for review.

Once App Store Connect has accepted a build number, never reuse it. If another binary must be uploaded, generate a new timestamp build number, update `project.yml`, run XcodeGen, review and commit the regenerated project, push the change, then archive again.

## 7. Wait for approval and public release

- [ ] Do not merge the version-bump PR while review is pending under the current project convention.
- [ ] Wait until the human confirms the App Store version is approved and publicly released.
- [ ] Preserve the release branch and archive until all post-release steps are complete.

## 8. Merge and tag the released source

- [ ] Merge the version-bump PR using the repository's normal merge-commit strategy.
- [ ] Pull the updated `master`.
- [ ] Identify the merge commit.
- [ ] Verify that the tagged source corresponds to the source used for the archive.

```sh
git switch master
git pull --ff-only origin master
MERGE_COMMIT="$(git rev-parse HEAD)"

git diff --exit-code "$ARCHIVED_COMMIT^{tree}" "$MERGE_COMMIT^{tree}"
```

> Footgun: tagging the merge commit identifies the uploaded binary only when its tree matches the archived release commit. If unrelated changes reached `master` while App Store review was pending, the trees may differ. Do not tag a mismatched merge commit. Stop and ask the human whether to tag the archived commit instead.

Create and push the lightweight tag after the tree check passes. This matches the existing `v2.0.1` tag precedent:

```sh
RELEASE_TAG="v$RELEASE_VERSION"

git tag "$RELEASE_TAG" "$MERGE_COMMIT"
git push origin "$RELEASE_TAG"
```

- [ ] Confirm the remote tag resolves to the intended commit.

## 9. Finish the release milestone

- [ ] Confirm every shipped PR is assigned to the `$RELEASE_VERSION` milestone.
- [ ] Confirm the now-merged version-bump PR is assigned to it.
- [ ] Close the milestone. Closing a milestone does not close its PRs.

```sh
gh api --method PATCH \
  "repos/$REPOSITORY/milestones/$MILESTONE_NUMBER" \
  --field state=closed
```

Verify its state and issue counts:

```sh
gh api "repos/$REPOSITORY/milestones/$MILESTONE_NUMBER" \
  --jq '[.title, .state, .open_issues, .closed_issues, .html_url] | @tsv'
```

## 10. Create the GitHub Release

Prepare a temporary Markdown file:

```md
## What's New

- Use the final user-facing App Store release notes.

## Engineering Notes

- Include this section only for significant non-user-facing improvements.
```

Screenshot rules:

- [ ] Attach screenshots only when the release contains visible new features.
- [ ] Prefer screenshots already attached to the shipped PRs.
- [ ] Ask the human which screenshots to use when selection is ambiguous.
- [ ] Use clear, stable filenames and helpful alt text.
- [ ] Do not run the App Store screenshot UI suite solely for the GitHub Release without explicit human approval. Its script also contains hardcoded simulator models and OS versions that may need updating.

If screenshots are selected, add a section using the predictable release-asset URLs:

```md
## Screenshots

![Feature description](https://github.com/twocentstudios/vinylogue/releases/download/v2.0.2/feature-name.png)
```

Create a non-draft, non-prerelease GitHub Release from the already-pushed tag. Attach any selected screenshots as release assets:

```sh
RELEASE_NOTES="<absolute-path-to-release-notes.md>"

# Without screenshots
gh release create "$RELEASE_TAG" \
  --repo "$REPOSITORY" \
  --verify-tag \
  --title "$RELEASE_TAG" \
  --notes-file "$RELEASE_NOTES"

# With human-approved screenshots
gh release create "$RELEASE_TAG" \
  --repo "$REPOSITORY" \
  --verify-tag \
  --title "$RELEASE_TAG" \
  --notes-file "$RELEASE_NOTES" \
  <screenshot-path-1> <screenshot-path-2>
```

- [ ] Verify the release is public, not a draft, and not a prerelease.
- [ ] Verify the tag, notes, and screenshot assets.

The `2.0.1` precedent used the tag/title `v2.0.1` and a concise `What's New` section.

## 11. Create the next minor-release milestone

Determine the next potential minor version and confirm it with the human. For example, after any `2.0.x` release, the next minor milestone is normally `2.1.0`, not `2.0.3`.

- [ ] Check for an existing milestone before creating one.
- [ ] Create it open with no due date unless the human supplies one.

```sh
NEXT_MINOR_VERSION="2.1.0"

gh api "repos/$REPOSITORY/milestones?state=all&per_page=100" \
  --paginate \
  --jq ".[] | select(.title == \"$NEXT_MINOR_VERSION\") | [.number, .state, .html_url] | @tsv"

gh api --method POST "repos/$REPOSITORY/milestones" \
  --field title="$NEXT_MINOR_VERSION" \
  --field description="Vinylogue $NEXT_MINOR_VERSION"
```

Create it only when the lookup returned nothing.

## 12. Final report

Report:

- App Store version and build number
- App Store public release confirmation
- Version-bump PR URL and merge commit
- Git tag and remote verification
- Closed release milestone URL
- GitHub Release URL
- Screenshot assets included, or explicitly `none`
- Next minor milestone URL
- Archive path retained locally
